# adamzr-plugin-marketplace

See [README.md](README.md) for the marketplace overview and plugin list, and
[CONTRIBUTING.md](CONTRIBUTING.md) for setup. This file is the rulebook for editing the repo.
`AGENTS.md` is a symlink to this file, so every agent reads the same rules.

## Validate before you commit

```bash
claude plugin validate --strict .
for p in plugins/*/; do claude plugin validate --strict "$p"; done
for p in plugins/*/; do claude plugin test "$p"; done   # mods with *.test.ts files
python3 scripts/validate.py --since main
ruff check . && ruff format --check .
```

These are the same checks CI runs (`.github/workflows/ci.yml`). Install the Python tools with
`pip install -r .github/requirements-ci.txt`. Run them after any edit to a plugin, and do
not hand work back without a clean run. If you touched `.github/`, also run
`actionlint && zizmor --persona pedantic .github/`.

## Two specs, one repo

The repo targets two specifications. **Claude Code is the priority: if they conflict,
Claude Code wins.**

| | Claude Code | [Agent Plugins 1.0.0](https://agent-plugins.org/specification) |
|---|---|---|
| Plugin manifest | `plugins/<name>/.claude-plugin/plugin.json` | `plugins/<name>/plugin.json` |
| Skills | `skills/<skill>/SKILL.md` | same |
| MCP servers | `.mcp.json` or inline | `mcp.json` only, never inline in `plugin.json` |
| Hooks, mod modules | `hooks/hooks.json`, `types/` | not defined; clients ignore them |
| Marketplace | `.claude-plugin/marketplace.json` | out of scope |

### The two manifests are separate files, not a symlink

`plugin.json` is a **closed schema** under Agent Plugins. Only `$schema`, `name`,
`version`, `description`, `author` (only `name` / `email` / `url`), `homepage`,
`repository`, `license`, `keywords`, and `extensions` are legal. `$schema` is required and
must be exactly `https://agent-plugins.org/schemas/1.0.0/plugin.schema.json`. The name must
match the folder name, use only `a-z 0-9 - .`, and start and end with a letter or digit.

Mods need Claude Code fields that are illegal there, such as `userConfig` and `types`. Those
fields only work from `.claude-plugin/plugin.json`: Claude Code 2.1.311 ignores `userConfig`
when it is moved to `marketplace.json` (verified, the plugin then reports "no options to
set"). So, unlike repos whose plugins have no Claude-only fields, the two files cannot be a
symlink:

- `.claude-plugin/plugin.json` holds every spec field **plus** the Claude-only fields.
- `plugin.json` holds `$schema` plus the spec fields, with identical values.

`scripts/validate.py` fails if any spec field differs between the two, so edit both together.
The JSON schemas it checks against are vendored in `scripts/schemas/` because the spec
forbids fetching schemas at load time. Refresh them only when moving to a new spec version.

A plugin with MCP servers declares them in `plugins/<name>/mcp.json` with `$schema` set to
`https://agent-plugins.org/schemas/1.0.0/mcp.schema.json` and only `mcpServers` beside it.

## Version management

Every change to a plugin, other than to its `README.md`, `LICENSE`, or `CHANGELOG.md`, must
bump its version in all three places:

1. `plugins/<name>/.claude-plugin/plugin.json`
2. `plugins/<name>/plugin.json`
3. The plugin's entry in `.claude-plugin/marketplace.json`

Use SemVer. Installed copies only update when the version changes, so a missed bump means
users never get the fix. `scripts/validate.py --since main` enforces all of this.

## Mods (hooks modules)

- Mod code is TypeScript under `hooks/`, listed in `hooks/hooks.json` under `modules`.
- Tests are `*.test.ts` files that import from `claude-code/testing`. Run them with
  `claude plugin test plugins/<name>`. Add or update a test for any behavior you change.
- `.claude-plugin/types/` is generated by Claude Code for editor type checking. It is
  ignored by git; never commit it.
- Load the `plugin-authoring` skill before changing a mod's hooks or engine calls.

## Skills

Skills must follow the [Agent Skills specification](https://agentskills.io/specification)
and Anthropic's
[skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices.md).
Frontmatter is a closed set (`name`, `description`, `license`, `compatibility`, `metadata`,
`allowed-tools`); anything else goes under `metadata:` as a string. Keep `description` under
1,024 characters with no XML-like tags, and quote any value containing `: `.

## Paths and portability

- Resolve files inside a plugin with `${CLAUDE_PLUGIN_ROOT}`. Never search for an installed
  copy, and never name a client-specific directory such as `~/.claude/plugins/cache/...`.
- Never commit a personal path such as `/Users/<someone>/...`.
- Plugin-relative paths in manifests start with `./` and must stay inside the plugin folder.
- Say so in the README when something is macOS-only.

## CI and GitHub Actions

- Pin every action to a full commit SHA with a `# vX.Y.Z` comment. Dependabot updates them.
- Workflows start with `permissions: {}` and grant each job the least it needs.
- Check out with `persist-credentials: false`.
- Pass `${{ }}` expressions into `run:` blocks through `env:`, never inline.
- Install tools from a lockfile or pinned requirements file, not with ad hoc
  `npm install` or `pip install <pkg>`. The Claude Code CLI is pinned in
  `.github/claude-code/package-lock.json`; Python tools in `.github/requirements-ci.txt`.
- `actionlint` and `zizmor --persona pedantic` must both be clean.

## Branch and merge workflow

`main` is protected. Work on a kebab-case branch, open a pull request, and let CI pass. Pull
requests are squash-merged and the branch is deleted on merge. Never force-push `main`.

## Writing style

Public docs, commit messages, and PR descriptions use American English and never use an em
dash or an en dash as punctuation. Rewrite the sentence instead.
